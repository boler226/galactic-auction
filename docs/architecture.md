# Архітектура системи «Галактичний аукціон артефактів»

## 1. Призначення та навантажувальний сценарій

Система проводить міжгалактичні аукціони артефактів у реальному часі.
Ключовий сценарій навантаження — **останні секунди торгів**: тисячі
учасників одночасно роблять ставки на один і той самий лот, а всі
спостерігачі мають миттєво бачити актуальну ціну через WebSocket.

Це створює дві головні проблеми:

1. **Race condition.** Кілька ставок надходять майже одночасно. Система
   має гарантувати, що виграє лише коректна (найвища й найраніша) ставка,
   а поточна ціна ніколи не «відкочується» назад.
2. **Fan-out.** Кожна прийнята ставка має бути розіслана всім
   підписникам лота з мінімальною затримкою.

## 2. Компоненти

| Компонент | Технологія | Роль | Статус |
|---|---|---|---|
| Клієнти | Браузер / мобільний клієнт | REST для каталогу, WebSocket для торгів | зовнішні |
| Балансувальник | Nginx | Розподіл HTTP/WS-трафіку між інстансами | заплановано |
| Backend | FastAPI + Uvicorn (async) | REST API, WebSocket, валідація ставок | **каркас готовий** |
| Кеш + Pub/Sub | Redis | Поточна ціна лота, розсилка подій між інстансами, атомарні операції | заплановано |
| База даних | PostgreSQL 16 | Джерело істини: користувачі, лоти, аукціони, ставки | **налаштовано** |
| Міграції | Alembic | Версіонування схеми БД | **налаштовано** |

## 3. Потік обробки ставки (цільова схема)

1. Клієнт відкриває WebSocket `/ws/auctions/{id}` і підписується на лот.
2. Клієнт надсилає ставку.
3. Балансувальник передає з'єднання на один із інстансів backend.
4. Backend валідує ставку (аукціон активний, сума вища за поточну, вистачає балансу).
5. Ставка проходить **атомарну перевірку** (див. розділ 4).
6. Прийнята ставка записується в PostgreSQL.
7. Подія публікується в Redis Pub/Sub.
8. Усі інстанси backend отримують подію й розсилають її своїм WebSocket-клієнтам.

## 4. Стратегії боротьби з race condition

| Рівень | Підхід | Коментар |
|---|---|---|
| БД | Оптимістичне блокування (колонка `auctions.version`) | Вже закладено в моделі. Конфліктна транзакція отримає `StaleDataError` |
| БД | `SELECT ... FOR UPDATE` на рядок аукціону | Песимістичне блокування, простіше, але створює чергу на «гарячому» рядку |
| Кеш | Атомарний Lua-скрипт у Redis (порівняти й оновити ціну) | Найшвидший варіант для гарячого лота |
| Застосунок | Послідовна обробка ставок одного лота (черга на лот) | Повне усунення гонок для конкретного лота |

Порівняння цих підходів під навантаженням буде предметом наступних
лабораторних робіт.

## 5. Горизонтальне масштабування

- Backend **stateless**: усі спільні дані лежать у PostgreSQL та Redis.
- Кількість інстансів backend можна збільшувати за балансувальником.
- Redis Pub/Sub гарантує, що учасник, підключений до інстансу A, бачить
  ставку, зроблену через інстанс B.
- Пул з'єднань з БД налаштовується через `DB_POOL_SIZE` / `DB_MAX_OVERFLOW`.

## 6. Модель даних

- `users` — учасники торгів (баланс, унікальні `username` та `email`).
- `artifacts` — артефакти (назва, рідкісність, галактика походження).
- `auctions` — торги по артефакту (ціни, статус, час початку/завершення, `version`).
- `bids` — історія ставок (`auction_id`, `user_id`, `amount`, час).
  Складений індекс `(auction_id, amount)` пришвидшує пошук найвищої ставки.

Зв'язки: `artifacts 1—N auctions`, `auctions 1—N bids`, `users 1—N bids`,
`auctions N—1 users` (поточний лідер торгів).
